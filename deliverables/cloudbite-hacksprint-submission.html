CLOUDBITE (v0.0.1) — DAYTONA HACKSPRINT SUBMISSION & PITCH SCENARIO (ENGLISH)
=============================================================================

1. Product Title, Hook, Problem & User Value
-----------------------------------------------------------------------------
- Product Title: Cloudbite — Multi-Expert Sandbox Decision Workbench
- One-Sentence Hook: Instead of asking one chatbot to role-play five experts and getting five unverifiable paragraphs, Cloudbite gives five AI specialists their own isolated Daytona computers and server-side Nosana inference so every opinion comes back with inspectable files, numbers, and explicit assumptions.
- Problem: When a team faces a launch decision, it needs product, finance, security, engineering, and design perspectives; asking a single chat thread yields confident prose where nobody can check where a number came from or what was assumed.
- User Value: A founder or project lead submits one shared project brief, dispatches role-specific work orders to isolated expert sandboxes that run Python and write real files, compares structured opinions and self-assessed confidence across decision options, and turns expert disagreements directly into the next concrete validation experiment.
  * Target-User Boundary: Targeting early product teams making launch decisions is our current product hypothesis. We make no claims of validated customer demand, paying customers, revenue, or pricing.


2. Main User Journey & Five-Expert Project Flow
-----------------------------------------------------------------------------
[Concrete Shared Brief]
- Decision Maker: A founder deciding whether to launch a 100-expert AI advisory service.
- Shared Project Question: "Should we launch a 100-expert AI advisory service right now (Full Launch), or start with a bounded Paid Pilot to measure unit economics and workflow reliability?"
- Delivery Mechanism: One validated brief (title, objective, context) is sanitized and written identically into `PROJECT.md` and `project.json` inside each selected expert's workspace.

[Selected 5 Roles (Chosen from the 12-Role Metadata-Derived Catalogue)]
* Catalogue & Scale Boundary: Cloudbite ships 12 metadata-derived AI expert roles built from the `Shinick-Han/pro-bably` registry seed (coverage tier T0; prompts freshly authored from metadata). A live project runs 1–5 selected experts with up to 3 concurrent sandboxes. 100 experts is the long-term product vision, not tested runtime capacity.
1) Product Manager (`agency-product-manager`) — Scope boundaries, launch criteria, phased roadmap (`out/prd.md`, `out/roadmap.md`)
2) Finance / FP&A Analyst (`agency-finance-fpa-analyst`) — Inference multiplier modeling, sensitivity table (`out/financial-model.md`, `out/forecast.csv`)
3) Security Architect (`agency-security-architect`) — Per-sandbox isolation boundaries, credential protection, threat model (`out/threat-model.md`, `out/security-controls.md`)
4) Software Architect (`agency-engineering-software-architect`) — Concurrency caps, Durable Object state machine, failure recovery (`out/architecture.md`, `out/adr-001.md`)
5) UX Architect (`agency-design-ux-architect`) — Multi-expert comparison flow, cognitive-load risks (`out/user-flows.md`, `out/ux-risks.md`)

The list above is a proposed five-role live selection from the actual catalogue. The offline preview uses its own authored role display names and embedded artifacts; these are examples, not live run outputs.

[Scene-by-Scene Product Flow]
- Scene A. Shared Brief -> Expert Workspaces, Personas & Work Orders:
  From the single brief, Cloudbite builds an isolated workspace pack for each of the 5 experts (`INSTRUCTIONS.md`, `PERSONA.md`, `PROJECT.md`, `project.json`, `WORKORDER.md`, `RESULT.schema.json`, `provenance.json`). Finance receives unit-economics questions while Security receives isolation and credential-boundary questions.
- Scene B. Isolated Execution & Inspectable Artifacts:
  Up to 3 experts run concurrently. Inside `/home/daytona/cloudbite` in its own Daytona sandbox, each expert runs `runner.py`, executes Python in `./work`, writes role artifacts to `out/`, and requests Nosana inference through the Cloudbite server gateway.
  Crucial proof point: Finance (`agency-finance-fpa-analyst`) does not merely say "100 experts is expensive." It leaves a cost-model artifact showing that under the same multi-turn assumptions (4 turns per expert), 100 experts require 400 inference calls versus 20 calls for 5 experts (20x inference volume), while leaving unmeasured provider unit prices as explicit variables rather than invented numbers.
- Scene C. Common Opinion Schema & Confidence Distribution (Full Launch):
  Every expert must output `out/result.json` matching the strict six-field `ExpertOpinion` schema (`direction`, `confidence`, `summary`, `evidence`, `assumptions`, `nextActions`) alongside `out/report.md`.
  In the scripted pitch walkthrough (`demo/cloudbite-pitch.html`), the **Full Launch** option produces **2 Support / 2 Conditional / 1 Concern** with an unweighted average self-assessed confidence of **82**.
  * Confidence Boundary: Confidence (integer 0–100) is each model's uncalibrated self-assessment—a signal displayed next to evidence, not statistical accuracy, expert consensus, or business success probability. Counts and averages are unweighted.
- Scene D. Paid Pilot Option Comparison:
  Switching the decision board from **Full Launch** to **Paid Pilot** (a bounded 5-expert, 3-concurrent pilot to measure real run costs first) shifts the authored sample distribution to **3 Support / 2 Conditional / 0 Concern** with an unweighted average self-assessed confidence of **84**.
- Scene E. Decision Brief Export & Next Validation:
  The user clicks `Save brief` to export the structured decision brief, turning disagreements and unverified cost variables into the immediate next experiment: run one real project end-to-end and measure actual sandbox and inference cost.

4. Sponsor Evidence & Technical Story (Daytona & Nosana)
-----------------------------------------------------------------------------
* Sponsor Rules Boundary: No sponsor event rules or judging rubrics were supplied, so no external prize criteria are invented here.

[Daytona — Isolated Per-Expert Execution & Inspectable File Outputs]
- Role in Architecture: Rather than multiplexing five personas in one prompt window, Cloudbite provisions a separate Daytona sandbox per expert (`/home/daytona/cloudbite`), uploads the validated workspace pack (`PERSONA.md`, `PROJECT.md`, `WORKORDER.md`, `RESULT.schema.json`, `runner.py`), and runs an isolated Python session (`timeout 600 python3 -I runner.py`).
- Why It Matters Practically: Each specialist can execute Python scripts in `./work` and write structured deliverables (`out/result.json`, `out/report.md`, and up to four role files such as `.csv` forecasts or `.md` threat models) without cross-contaminating another expert's filesystem or environment. Claim-label deduplication and bounded cleanup (`autoStopInterval 20`, `autoDeleteInterval 30`, plus 8-try backoff deletion) reduce duplicate creation and provide bounded cleanup retries; they do not guarantee that every external cleanup succeeds.
- Verified Evidence on Hand: `demo/evidence.json` (generated by `demo/run-council.ps1`) records three real Daytona sandboxes provisioned, executing remote Python analysis, and cleaning up cleanly.

[Nosana — Server-Side Inference Gateway Driving the Reasoning Loop]
- Role in Architecture: Inside each sandbox, `runner.py` reads and immediately deletes its short-lived capability file (`.cloudbite/capability.json`) and calls the Cloudbite worker gateway (`/p/_cloudbite/worker/<project>/<run>/inference`) using its per-expert `cbw_...` token. The server (`src/cloudbite-inference.ts`) proxies bounded requests to the configured OpenAI-compatible Nosana `chat/completions` endpoint using server-held credentials.
- Why It Matters Practically: Upstream Nosana credentials never enter browser responses, prompts, or sandbox files. The server enforces strict per-expert budgets (up to 6 runner turns, max 8 gateway calls reserved before upstream fetch, one in flight, <= 48 KiB body, `max_tokens` 1200) and revokes capability hashes atomically on project cancellation so late inference calls immediately receive `410`.
- Verified Evidence on Hand: The Nosana gateway module, capability enforcement, cancellation cutoff, and real local Python runner pass 18 runtime integration checks against deterministic stand-in providers. The first full live Nosana E2E run is our immediate next validation step.

[Why Both Matter Together]
- Nosana supplies the multi-turn reasoning that decides what analysis to run and synthesizes findings into the common `ExpertOpinion` schema; Daytona supplies the isolated computer where that analysis actually executes and leaves verifiable files. Together they replace uncheckable chat paragraphs with inspectable work.

[Daytona — 전문가별 격리 실행 환경과 파일 증거]
- 역할: 전문가마다 다른 프롬프트만 주는 것이 아니라, `/home/daytona/cloudbite` 경로를 가진 독립된 Daytona 샌드박스를 생성해 `PERSONA.md`, `PROJECT.md`, `WORKORDER.md`, `runner.py`를 업로드하고 격리된 Python 세션(`timeout 600 python3 -I runner.py`)을 실행합니다.
- 왜 필요한가: 재무 모델 계산이나 아키텍처 검증이 다른 전문가의 파일이나 환경 변수와 섞이지 않으며, 실행 결과물(`out/result.json`, `out/report.md`, 역할별 `.md/.csv`)을 서버가 다운로드해 스키마 검증 후 사용자에게 그대로 보여 줄 수 있습니다. 또한 라벨 기반 중복 생성 방지와 자동 정리(`autoStopInterval 20`, `autoDeleteInterval 30` 및 8회 백오프 정리)로 중복 생성 및 정리 실패 위험을 줄입니다.
- 검증된 증거: `demo/run-council.ps1`로 생성된 `demo/evidence.json`에 실제 Daytona 샌드박스 3개를 순차 생성하고, 원격 Python 분석 스크립트를 실행한 뒤 정리까지 완료한 기록이 남아 있습니다.

[Nosana — 서버 게이트웨이 기반 멀티턴 추론 루프]
- 역할: 각 샌드박스 내부의 `runner.py`는 Nosana API 키를 직접 갖지 않고, 만료와 작업별 범위 제한이 적용된 워커 토큰(`cbw_...`)으로 서버 게이트웨이(`/p/_cloudbite/worker/<project>/<run>/inference`)를 호출합니다. 서버(`src/cloudbite-inference.ts`)가 OpenAI 호환 Nosana `chat/completions` 엔드포인트로 요청을 중계합니다.
- 왜 필요한가: 브라우저나 샌드박스 내부에 공급자 비밀키를 노출하지 않으면서, 전문가당 최대 6턴(게이트웨이 상한 8회 호출, 48 KiB 요청, 1200 토큰 응답 제한) 동안 Python 실행(`python`) -> 파일 작성(`write`) -> 최종 스키마 검증(`final`)으로 이어지는 추론 루프를 구동합니다. 작업이 취소되면 캡슐 해시가 즉시 폐기되어 늦게 도착한 추론 호출은 `410`으로 차단됩니다.
- 검증된 증거: 게이트웨이 라우팅, 토큰 한도, 취소 차단, 로컬 Python 러너를 포함한 18개 런타임 통합 테스트가 대체(stand-in) 공급자 환경에서 통과했습니다. 실제 라이브 Nosana 엔드포인트 E2E 호출은 다음 검증 단계입니다.

[두 기술의 결합 의미]
- Daytona가 "전문가가 실제로 코드를 돌려 파일을 남기는 격리된 작업실"이라면, Nosana는 "그 작업실에서 어떤 계산을 수행하고 어떤 근거로 결론을 맺을지 결정하는 추론 엔진"입니다. 두 계층이 합쳐져야 단순 채팅이 아닌 '검증 가능한 작업 산출물 기반 의사결정'이 완성됩니다.
