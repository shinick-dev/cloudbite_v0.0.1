# Product v3 — console UI

The browser console (`client/cloudbite-console.ts` → generated `src/cloudbite-page.ts`) shows three
v3 server fields in KO/EN. It reads and displays them; it never computes or verifies them itself.
Server contracts: `docs/provenance-v3.md`, `docs/artifact-review-v3.md`, `docs/author-response-v3.md`.

## 1. Claim provenance (`ProjectRun.provenance {ledger, state}`)

- **Strict normalization.** Version, `projectId`, snapshot, claim ids, origins/kinds, refs,
  `adoptedIn` iff `parent-adoption`, `factsVerified/sourcesRetrieved === false`, adoption `meaning`.
  Any mismatch drops the whole field and the screen says it cannot read the provenance (no adopt
  buttons). Claim text is kept unclipped. Claim and adoption text are bounded at 1000 **code
  points**, as the server clips and parses them (`[...text].length`), not UTF-16 units: a valid
  1000-emoji claim (UTF-16 length 2000) is accepted with its `textTruncated` flag and raw snapshot
  as sent; 1001 code points drops the field. All other bounds are unchanged.
- **Standing** mirrors the server's `effectiveAdoptions`/`claimStanding`: user-stated,
  user-adopted, carried (parent adoption), generated proposal. Adoptions whose claim/snapshot no
  longer match are counted as stale.
- **Groups**, collapsed by default: numeric/threshold proposals (highlighted as *proposals, not
  requirements*), adopted, other proposals, own statements. Items render only when a group is
  opened, 50 at a time ("Show more"), so a ledger of thousands of claims is not drawn eagerly.
  Origin/standing details sit in a further collapsed disclosure per claim.
- **Adopt authority.** Only the project's own user may adopt (server `historyAdopt`: own history
  actor). The console's only proof is `HistoryDetail.canFeedback` (own actor && terminal) from a
  history detail the server returned; the project bearer of the current run is **not** history
  authority. A terminal detail with `canFeedback: false` (e.g. an owner reading another user's
  project in the "all" scope) shows "only the project's own user can adopt" and no Adopt button.
  On the current run, where ownership is not yet known, Adopt… first GETs
  `/api/cloudbite/history/{id}` (session cookie / explicit admin header, no fallback) and opens the
  confirm step only when that detail says `canFeedback: true`; 401 → "sign-in not accepted, nothing
  adopted", 403/`canFeedback: false` → "not your project", 404 → not found, unreadable → "nothing
  was sent". None of these POST, sign the user out or clear the history view.
- **Adopt.** For a finished live project with no review or memo running, for non-truncated
  generated claims, with the authority above. The first click shows the exact claim text and a
  note that adoption is not verification and the original memo stays unchanged; only the explicit
  confirm button POSTs `/api/cloudbite/history/{id}/adopt` with exactly `{claimId, text, snapshot}`
  through the existing `historyRequest` helper (session cookie / admin header). No client actor or
  time is sent.
- **Reconciliation.** A 200 `HistoryDetail` replaces the detail and the provenance on the current
  run view. Any failure (409 stale/text mismatch/already adopted, 404 foreign or deleted, 401/403,
  network/unknown) shows the reason and then GETs the saved detail **before** the button is offered
  again; if the re-read already shows the adoption, it says so. A retry uses the re-read snapshot.
  403 says "not your project", never "sign in". When the POST outcome is unknown (network, or 200
  with an unreadable body) **and** that re-read also fails, the screen says the state is unknown
  and to read it again or reload; no Adopt button is offered for that project from the
  unreconciled state, only a GET-only "Read the saved state again" button, repeatable until a read
  succeeds (a response for another project is discarded). After a successful read it shows
  "already adopted" or lets the user adopt again with the fresh snapshot.
  The memo is never regenerated by adoption.
- **Export.** JSON keeps the normalized field; Markdown adds a "Claim provenance" section
  (counts, stale/carried/invalid notes, adopted and numeric-proposal claims).

## 2. Artifact coverage (`crossReview.artifactCoverage[]`)

Per reviewer role: packet hash, files with path / sha256 / line range of total / excerpt-cut /
stored-cut, and omitted files with the server's reason. Shown under the cross-review reports and in
the Markdown export with the explicit note that reviewers read stored text only — no code was run,
no data parsed, nothing independently verified. A malformed coverage drops only that field
(`invalidArtifactCoverage`); verdicts stay.

## 3. Author response

- `previousRound.authorResponse` (`AuthorResponsePlan`) is normalized strictly (parent id, zero
  automatic calls, findings belonging to their authors). Invalid → round kept, plan marked
  unreadable.
- `ExpertRun.authorResponse` is `AuthorResponseParsed` or `{invalid}`; an unreadable shape is
  marked separately. Per author: original opinion (earlier project, unchanged), response status
  (complete/partial/none, server-rejected, unreadable, pending) kept **separate from the role's
  opinion status**, and per finding revise / withdraw / maintain + rationale or "no response".
  The child's own opinion is shown as usual and is not merged with the original.
- **Ask authors to respond.** On a terminal, non-cancelled live project whose cross-review is
  completed, the button opens the existing follow-up draft preselecting only *affected* authors
  (completed roles targeted by a challenged/insufficient finding from another completed role on an
  existing evidence index). Routing is forced to manual; selecting a non-affected role or none
  blocks the plan. `revision {parentId, changeSummary, reviewSnapshotHash: parent.crossReview.snapshotHash}`
  goes into the frozen preview body, which is sent byte-identical on create; normalization keeps the
  hash. The user still goes through Prepare plan → Run confirmation; nothing is paid for
  automatically and the child has its normal budget. The ordinary follow-up is unchanged (no hash).
  Stale hash / foreign parent are rejected by the server.

## Checks

`npm run build:cloudbite-console`, `node tools/build-cloudbite-console.mjs --check`,
`npx tsc -p tsconfig.client.json`, `node test/cloudbite-v3-ui.mjs`, plus the existing
`cloudbite-workflow-ui`, `cloudbite-console`, `cloudbite-decision-ui` tests.

## Limits

Fake-DOM tests only — no real browser, server, Durable Object or provider run in this change. The
console trusts the server for standing rules, coverage and affected-finding selection beyond the
shape checks above; the client-side "affected" list is a UI preselection, the server remains the
authority.
