The custom domain attaches to the existing cloudbite-v001 Worker. State, CloudbiteProject,

same path on cloudbite.shinick.dev. Its old browser APIs return 410 with the new origin;
credential-bearing requests are never replayed across origins. CLOUDBITE_CANONICAL_ONLY=1
enables this policy. The old hostname remains technically reachable for the security-key
RP document and authenticated /p/ sandbox gateway paths only. Do not disable workers_dev
or delete cloudbite-v001: the custom domain uses that same Worker and its existing data.

Zone routing prerequisite: the existing *.shinick.dev/* -> gw-shinick route takes priority
over Custom Domains. A narrower cloudbite.shinick.dev/* -> Workers disabled (no script)
exception lets this hostname reach its cloudbite-v001 Custom Domain. Keep that exact
exception in the shinick.dev zone Workers Routes; do not remove or edit the wildcard.
Wrangler manages this app's Custom Domain; the no-script exception is managed in the
Cloudflare zone dashboard, like the existing console.shinick.dev/* exception.

Security keys keep RP ID cloudbite-v001.ai-gongbu.workers.dev. The original RP serves
/.well-known/webauthn with the exact two permitted origins. Related Origin Requests let
compatible browsers use the existing key at the custom origin; no credential is copied or
re-registered. The server verifies the exact allowed origin/RP pair, signed challenge and UV.
This is not a wildcard domain allowance and does not authorize legacy admin/vault ceremonies
from the custom origin. HTTP POST Origin must still match the receiving origin exactly.

Chrome supports Related Origin Requests from version 128:
https://developer.chrome.com/blog/passkeys-updates-chrome-129
Use an up-to-date browser with this feature for existing security keys on the new origin.

Cookies and browser-local project history are origin-specific. An existing logged-in browser
must sign in once at the new host. Old links redirect, but origin-local project history and
visitor cookies do not transfer. Old credential records and server-side project data remain.
Logging out revokes the specific owner session, as before; it does not log out other browsers
or a separately authenticated origin. Visitor approval records share the same inbox but a
visitor must keep using the origin where they requested access (cookies do not migrate).
