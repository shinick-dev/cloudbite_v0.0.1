Cloudbite audience access — backend (src/cloudbite-access-service.ts, src/cloudbite-access-api.ts)
=================================================================================================

Purpose: a visitor (QR at the event) asks Cloudbite itself for access; the owner signs in with a registered security
key and approves using a persistent Cloudbite owner cookie (owner-session.txt). Temporary cbo_ operator tokens and
Cloudbite State admin sessions remain fallback credentials. The approved browser may then create up to TEN
Cloudbite projects of its own. Nothing here touches gw-shinick, its admin, vault or studyroom routes.
Wire shapes: src/cloudbite-access-contract.ts (CloudbiteAccessRequest, CloudbiteAccessSession).

Routes (all on the Cloudbite Worker ORIGIN)
  POST /api/cloudbite/access/requests              public. Body {name, purpose}, exact Origin, application/json,
                                                   <= 8 KiB, no other fields. name 1-80 (no control chars),
                                                   purpose 1-1000 (newline/tab allowed). Both trimmed and stored
                                                   as PLAIN TEXT — any UI must render them as text, never HTML.
                                                   201 + Set-Cookie for a new request; 200 and no new cookie when
                                                   this browser already holds a pending/approved unexpired request.
                                                   Response: CloudbiteAccessSession.
  GET  /api/cloudbite/access/status                the cookie's CloudbiteAccessSession, or {request:null,canCreate:false}.
                                                   Runs the failed-run refund check first (below).
  GET  /api/cloudbite/access/requests              owner cookie or x-admin-token. {requests: [...]} newest first, max 100.
  POST /api/cloudbite/access/requests/<id>/approve owner only, exact Origin, JSON body exactly {}.
  POST /api/cloudbite/access/requests/<id>/deny    "
  POST /api/cloudbite/access/requests/<id>/revoke  "    Each returns CloudbiteAccessRequest.
  GET  /api/cloudbite/bootstrap                    adds .access only when the binding exists AND a cookie is sent;
                                                   otherwise byte-for-byte the previous bootstrap.
  POST /api/cloudbite/projects                     unchanged for x-admin-token callers. With NO x-admin-token, the
                                                   owner cookie is checked before an approved visitor cookie (Quota). A wrong
                                                   admin header is never rescued by a cookie.

Owner check: an explicit x-admin-token decides alone: cbo_ prefix -> verifyCloudbiteOperator (never reaches State);
anything else -> State.adminList. Without that header, check the Cloudbite owner cookie. The persistent cookie is
issued only after verified WebAuthn, and logout revokes it server-side. Only these Cloudbite paths use it; no legacy bypass.

Visitor credential
  cbv_ + base64url(32 random bytes). Only its SHA-256 is stored (cred:<hash> index + record field); the plaintext
  exists only in the Set-Cookie header. Never in JSON, lists, URLs, logs or browser storage.
  Cookie: __Host-cb-access=<cbv_>; Path=/; Max-Age=5400; HttpOnly; SameSite=Strict; Secure
  Local http dev only (CLOUDBITE_ALLOW_HTTP=1 AND ORIGIN starts with http:): cb-access-dev, same attributes without
  Secure (a __Host- cookie requires Secure). Each mode reads only its own cookie name.
  Request ids authenticate nothing: status/bootstrap/create look up the cookie hash only.

Lifecycle (server clock)
  pending  -> approved   approve; grant lasts 1 h from approval (expiresAt updated)
  pending  -> denied     deny
  approved -> revoked    revoke
  pending/approved past expiresAt read as "expired" (pending window 30 min).
  Re-applying the current action is idempotent (200, same view). Every other transition is 409: nothing revives an
  expired, denied or revoked request. A new submit from that browser then creates a new request + new cookie.
  maxExperts 5 per run, maxProjects 10, usedProjects 0-10 (non-refunded slots, in flight or created).

Storage: one CloudbiteAccess DO, getByName('hacksprint-2026-10-18'), SQLite-backed class (migration v2), KV API.
  req:<id>       record (public fields, credHash, projects[] = {id, holds, confirmed} slots, refunds, refunded)
                 Records written while the quota was one project carry projectRequestId/holds/confirmed instead;
                 every method reads them as a one-slot list (same id, holds and confirmation; refunds/refunded kept)
                 and the next write stores projects[] and drops the legacy fields. A grant approved under the old
                 quota therefore reads maxProjects 10, usedProjects 1 and may create nine more.
  cred:<sha256>  -> id
  rate:<sha256>  creation times within the last hour for a hashed source
  Every method runs in one in-object serial queue and does storage I/O only; related keys are written in one put().
  Bounds: 120 new requests per source per hour (source = SHA-256 of MASTER_KEY + cf-connecting-ip; the raw address is
  never stored; attendees at a venue often share one NAT address, so the rate is sized for a room), 100 pending,
  500 retained; records that ended (expired/denied/revoked) are deleted 8 h after
  they ended, on the next submit. No provider, sandbox or paid resource is touched by request, approval or status.

Quota and tenant isolation (POST /api/cloudbite/projects with a visitor cookie)
  1. grant check (approved, unexpired) -> 401 otherwise.
  2. validateBrief against the actual catalogue (1-5 experts), live configuration check — before any reservation.
  3. brief.requestId := SHA-256('cloudbite-visitor-v1|' + access request id + '|' + raw requestId) (64 hex), so two
     visitors (or a visitor and the owner) sending the same raw requestId get different project ids; idempotent
     create can never hand a visitor a token for someone else's project. The project's brief.requestId is this
     scoped value. Owner/operator creates are unchanged (raw requestId).
  4. reserve(): atomically binds one of the grant's 10 slots to that scoped requestId. An id the grant already
     holds = retry (returns the same project with another cbt_ token, within the existing 4-token limit) and takes
     no further slot, even at full quota. A new id with 10 slots used = 409. Concurrent creates serialize in the DO,
     so eleven distinct concurrent creates yield exactly ten projects. A refunded id is refused (409).
  5. Definite refusal before anything was created (registry 429, create 400/503) -> release() of that id only:
     frees that slot only if no other attempt for the same id is in flight and none succeeded. Success or 409
     (project exists) -> confirm() of that id: that slot is permanent. A thrown/indeterminate create keeps its slot
     (conservative: the visitor may retry the same requestId; the slot counts toward the 10). Confirm/release
     never touch another id's slot or another grant's record.
  Revoked or expired grants cannot create or retry.

Failed-run refund (a definitively failed run gives its slot back)
  Runs on GET /api/cloudbite/access/status, GET /api/cloudbite/bootstrap (with a cookie) and before every visitor
  reserve. No new endpoint, no browser-supplied id: the Worker
    1. asks CloudbiteAccess.refundCandidate(credHash) (read-only): the stored scoped requestIds of every slot that is
       confirmed with holds == 0 (nothing in flight, no unconfirmed create), only while the grant is approved and
       unexpired (at most 10), plus how many refunds the grant has left;
    2. asks CloudbiteProject.refundState(scoped) on getByName(cbProjectId(scoped)) for each of them, independently
       (an internal read-only DO method, never routed from HTTP) that re-checks project.brief.requestId == scoped
       and answers
         refundable  status failed (zero completed experts), every expert final, every cleanup entry done and none
                     stuck, live slot released (live mode)
         cleanup     failed with zero completed, cleanup/slot not confirmed yet
         none        missing/purged, running, completed, partial, cancelled, stuck cleanup, other requestId;
       an exception (or a missing CLOUDBITE binding) for one project counts as unavailable for that slot only;
    3. any refundable and refunds left -> CloudbiteAccess.refund(credHash, [scoped...]): compare-and-clear per id in
       the serial queue (grant approved/unexpired, still holds a slot for exactly that id, confirmed, holds 0,
       refunds < cap). Each cleared slot is removed, refunds += 1 and the id is remembered in refunded[]; other
       slots are untouched. reserve() refuses a refunded scoped id (409), so the failed run is never rebound — the
       visitor starts a new run with a new requestId. A stale/foreign/duplicate id is a no-op; concurrent refreshes
       refund once; a reserve that lands between steps 1 and 3 (holds > 0) wins.
  Fail closed: an exception from a project check, a missing CLOUDBITE binding or any other state keeps that slot.
  Cap: CB_ACCESS_MAX_FAILED_REFUNDS = 3 per grant, so one grant creates at most 10 + 3 projects in total, and every
  refunded one definitively failed with zero completed experts. Several refundable runs in one settle are refunded
  in stored order until the cap; the rest keep their slots.
  canCreate = approved, unexpired and usedProjects < 10 — a slot whose check failed or is still cleaning up never
  blocks the others. Session field recovery appears only while NO slot is free (canCreate false on an approved
  grant) and at least one settled slot failed with zero completed without being returned:
    unavailable  a project check failed (fail closed; the console re-reads bootstrap every 5 s, 24 times, plus
                 "Check again")
    pending      cleanup not confirmed yet (same re-read)
    limit        a refundable run remains but the cap is used up (final; ask the host for a new session)
  (checked in that order).
  Records written before refunds existed have no refunds/refunded fields and read as 0/[]: an already-failed grant
  recovers on its next status/bootstrap after deployment. Refunds never touch the failed project: its cbt_ token,
  activity and artifacts stay readable under the 24 h project policy.
  Console (not changed here): after a visitor's live run reaches a terminal status it re-reads bootstrap and enables Run again only when
  the server reports canCreate. Nothing starts automatically and the failed run stays on screen until the visitor
  selects Run again (a new requestId). Owner/operator runs are unchanged.
 Project cbt_ tokens already issued keep the existing 24 h
  project policy (CB_RETENTION); revocation does not reach into an already-created project.
