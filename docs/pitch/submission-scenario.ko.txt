CLOUDBITE (v0.0.1) — DAYTONA HACKSPRINT 제출 및 발표 통합 시나리오 (한국어 마스터)
====================================================================================

1. 제품 제목 및 핵심 정의 (Product Title & One-Sentence Hook / Problem / User Value)
------------------------------------------------------------------------------------
- 제품 제목: Cloudbite — 격리된 전문가 샌드박스 기반 의사결정 워크벤치 (Multi-Expert Sandbox Decision Workbench)
- 한 줄 훅 (Hook): 챗봇 하나에 다섯 역할을 시켜 출처 없는 문단 다섯 개를 받는 대신, 다섯 명의 AI 전문가에게 각자의 격리된 Daytona 컴퓨터와 Nosana 추론을 부여해 검증 가능한 파일·수식·가정이 담긴 의견을 받습니다.
- 핵심 문제 (Problem): 제품 출시 여부를 결정할 때 제품·재무·보안·기술·디자인 관점이 모두 필요하지만, 단일 채팅창에서 얻은 답변은 숫자의 출처와 전제 조건을 확인할 수 없습니다.
- 사용자 가치 (User Value): 하나의 공통 프로젝트 브리프를 여러 전문가 페르소나에게 배분하고, 각 전문가가 독립된 작업 공간에서 직접 코드를 돌리고 남긴 산출물(모델, 표, 아키텍처 문서)과 공통 스키마의 의견·가정·반론을 대조해 다음 검증 실험을 결정합니다.
  * 대상 고객 경계: "출시 결정을 내리는 초기 제품 팀"은 현재 팀의 가설(hypothesis)이며, 검증된 고객 수요·유료 고객·매출·가격 정책을 주장하지 않습니다.


2. 핵심 사용자 여정 및 5인 전문가 프로젝트 흐름 (Main User Brief & End-to-End Flow)
------------------------------------------------------------------------------------
[공통 브리프 (Shared Brief)]
- 의사결정 주체: 100인 전문가 AI 자문 서비스 출시 여부를 고민 중인 창업자.
- 공통 프로젝트 질문: "100명의 전문가 AI 자문 서비스를 지금 전면 출시(Full Launch)할 것인가, 아니면 범위가 제한된 유료 파일럿(Paid Pilot)으로 먼저 검증할 것인가?"
- 전달 방식: 제목·목표·맥락이 담긴 단일 브리프가 검증·정제되어 각 작업 공간의 `PROJECT.md`와 `project.json`으로 동일하게 주입됩니다.

[선택된 5개 전문가 역할 (12개 메타데이터 기반 카탈로그 중 선택)]
* 카탈로그 경계: `Shinick-Han/pro-bably` 레지스트리 시드 메타데이터(T0)에서 도출해 새로 작성한 12개 역할 중 5개를 선택합니다. 프로젝트당 1~5명 선택, 동시 실행 최대 3명입니다. 100인 자문은 장기 제품 비전이며 현재 검증된 런타임 용량이 아닙니다.
1) Product Manager (`agency-product-manager`) — 범위 정의, 출시 기준, 로드맵 (`out/prd.md`, `out/roadmap.md`)
2) Finance / FP&A Analyst (`agency-finance-fpa-analyst`) — 추론 호출 배수 계산, 단위 비용 민감도 모델 (`out/financial-model.md`, `out/forecast.csv`)
3) Security Architect (`agency-security-architect`) — 샌드박스 격리 경계, 자격증명 노출 방지, 위협 모델 (`out/threat-model.md`, `out/security-controls.md`)
4) Software Architect (`agency-engineering-software-architect`) — 동시 실행 제한, 상태 기계, 장애 복구 설계 (`out/architecture.md`, `out/adr-001.md`)
5) UX Architect (`agency-design-ux-architect`) — 다중 전문가 산출물 비교 화면, 정보 과부하 위험 (`out/user-flows.md`, `out/ux-risks.md`)

위 목록은 실제 카탈로그에서 선택할 5인 구성안입니다. 오프라인 프리뷰의 역할 표시명과 내장 산출물은 별도의 작성된 예시이며, 라이브 실행 결과가 아닙니다.

[장면별 제품 흐름 (Scene-by-Scene Flow)]
- 장면 A. 브리프 입력 -> 전문가 작업실 및 작업 지시서 생성:
  공통 브리프가 확정되면 5명의 전문가마다 독립된 작업 공간 세트가 구성됩니다(`INSTRUCTIONS.md`, `PERSONA.md`, `PROJECT.md`, `project.json`, `WORKORDER.md`, `RESULT.schema.json`, `provenance.json`). 재무 전문가는 단위 경제성 질문을, 보안 전문가는 격리 및 권한 경계 질문을 각자의 `WORKORDER.md`로 받습니다.
- 장면 B. 격리 실행 및 검증 가능한 산출물 생성:
  최대 3개의 작업 공간이 동시에 실행됩니다. 각 전문가는 자신의 Daytona 샌드박스(`/home/daytona/cloudbite`) 안에서 `runner.py`를 통해 Python 코드를 실행하고 `out/` 디렉터리에 파일을 기록하며, 서버 게이트웨이를 통해 Nosana 추론을 호출합니다.
  핵심 예시로 재무 전문가(`agency-finance-fpa-analyst`)는 단순히 "비용이 많이 든다"고 답하는 대신 비용 모델 산출물을 남깁니다. 동일 가정(전문가당 멀티턴 추론 4회)에서 5명 팀은 20회 추론이지만 100명 팀은 400회로 추론량이 20배가 되며, 아직 실측하지 않은 외부 단가는 임의로 꾸며내지 않고 명시적 변수로 남겨 둡니다.
- 장면 C. 공통 의견 스키마 및 확신도 분포 확인 (Full Launch 기준):
  모든 전문가는 `out/result.json`에 동일한 6개 필드 스키마(`direction`, `confidence`, `summary`, `evidence`, `assumptions`, `nextActions`)와 `out/report.md`를 반환합니다.
  전면 출시(Full Launch) 대안에 대한 샘플 시나리오 결과는 **추진(Support) 2 / 조건부(Conditional) 2 / 우려(Concern) 1**, 단순 평균 확신도 **82**입니다.
  * 확신도 경계: 확신도(0~100)는 각 모델의 자기 평가(self-assessment) 신호일 뿐 보정된 정확도나 사업 성공 확률이 아니며, 집계 역시 가중치 없는 단순 개수와 평균입니다.
- 장면 D. 유료 파일럿(Paid Pilot) 대안 비교:
  화면 상단 대안을 전면 출시(Full Launch)에서 유료 파일럿(Paid Pilot, 5인 전문가·동시 3인 제한으로 실측 먼저 수행)으로 전환하면, 분포가 **추진(Support) 3 / 조건부(Conditional) 2 / 우려(Concern) 0**, 단순 평균 확신도 **84**로 이동합니다(오프라인 피치 파일에 작성된 샘플 데이터 기준).
- 장면 E. 브리프 내보내기 및 다음 검증 전환:
  사용자는 `Save brief`로 의사결정 브리프 텍스트를 내보냅니다. 전문가 간 의견 차이와 미검증 가정은 곧바로 다음 실험 과제가 됩니다: "100명으로 확장하기 전에 실제 프로젝트 1건을 끝까지 돌려 추론 및 샌드박스 실측 단가를 확보한다."

4. 스폰서별 기술 스토리 및 근거 (Sponsor Evidence & Why Both Matter)
------------------------------------------------------------------------------------
* 스폰서 이벤트 규칙 경계: 별도의 스폰서 심사 배점표나 이벤트 특별 규칙이 제공되지 않았으므로, 임의의 심사 기준을 꾸며내지 않고 실제 구현과 기록된 실행 증거만 기술합니다.

[Daytona — 전문가별 격리 실행 환경과 파일 증거]
- 역할: 전문가마다 다른 프롬프트만 주는 것이 아니라, `/home/daytona/cloudbite` 경로를 가진 독립된 Daytona 샌드박스를 생성해 `PERSONA.md`, `PROJECT.md`, `WORKORDER.md`, `runner.py`를 업로드하고 격리된 Python 세션(`timeout 600 python3 -I runner.py`)을 실행합니다.
- 왜 필요한가: 재무 모델 계산이나 아키텍처 검증이 다른 전문가의 파일이나 환경 변수와 섞이지 않으며, 실행 결과물(`out/result.json`, `out/report.md`, 역할별 `.md/.csv`)을 서버가 다운로드해 스키마 검증 후 사용자에게 그대로 보여 줄 수 있습니다. 또한 라벨 기반 중복 생성 방지와 자동 정리(`autoStopInterval 20`, `autoDeleteInterval 30` 및 8회 백오프 정리)로 중복 생성 및 정리 실패 위험을 줄입니다.
- 검증된 증거: `demo/run-council.ps1`로 생성된 `demo/evidence.json`에 실제 Daytona 샌드박스 3개를 순차 생성하고, 원격 Python 분석 스크립트를 실행한 뒤 정리까지 완료한 기록이 남아 있습니다.

[Nosana — 서버 게이트웨이 기반 멀티턴 추론 루프]
- 역할: 각 샌드박스 내부의 `runner.py`는 Nosana API 키를 직접 갖지 않고, 만료와 작업별 범위 제한이 적용된 워커 토큰(`cbw_...`)으로 서버 게이트웨이(`/p/_cloudbite/worker/<project>/<run>/inference`)를 호출합니다. 서버(`src/cloudbite-inference.ts`)가 OpenAI 호환 Nosana `chat/completions` 엔드포인트로 요청을 중계합니다.
- 왜 필요한가: 브라우저나 샌드박스 내부에 공급자 비밀키를 노출하지 않으면서, 전문가당 최대 6턴(게이트웨이 상한 8회 호출, 48 KiB 요청, 1200 토큰 응답 제한) 동안 Python 실행(`python`) -> 파일 작성(`write`) -> 최종 스키마 검증(`final`)으로 이어지는 추론 루프를 구동합니다. 작업이 취소되면 캡슐 해시가 즉시 폐기되어 늦게 도착한 추론 호출은 `410`으로 차단됩니다.
- 검증된 증거: 게이트웨이 라우팅, 토큰 한도, 취소 차단, 로컬 Python 러너를 포함한 18개 런타임 통합 테스트가 대체(stand-in) 공급자 환경에서 통과했습니다. 실제 라이브 Nosana 엔드포인트 E2E 호출은 다음 검증 단계입니다.

[두 기술의 결합 의미]
- Daytona가 "전문가가 실제로 코드를 돌려 파일을 남기는 격리된 작업실"이라면, Nosana는 "그 작업실에서 어떤 계산을 수행하고 어떤 근거로 결론을 맺을지 결정하는 추론 엔진"입니다. 두 계층이 합쳐져야 단순 채팅이 아닌 '검증 가능한 작업 산출물 기반 의사결정'이 완성됩니다.
