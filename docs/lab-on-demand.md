# 참여자 요청으로 실습실 열기

참여자는 **https://k.shinick.dev/lab/request**, 모임지기는 **https://k.shinick.dev/lab/requests**를 사용합니다. 참여자 앱 첫 화면과 `/lab` 관리 화면에도 각각 연결이 있습니다.

## 참여자

1. 이름·원하는 작업을 적고 개인 복습 또는 모임 자리 추가를 고릅니다. 이름은 요청자가 적은 표시명이며 본인 인증을 뜻하지 않습니다. 연락처·비밀번호·개인 문서를 적지 않습니다.
2. 요청은 서버에 보관되고 24시간 동안 승인 대기할 수 있습니다. 이 브라우저에서 다시 열면 같은 요청을 확인할 수 있습니다.
3. 승인 뒤 같은 화면의 **내 실습실로 이동**을 누릅니다. 입장 페이지에서 편집기가 실제로 준비됐는지 확인합니다. 링크 발급과 편집기 준비는 다른 단계입니다.
4. 결과는 저장하고 **내 작업 받기**로 내려받아 내 PC에서 직접 확인합니다. 실습실은 승인한 시간이 끝나면 정리됩니다.

확인용 비밀값은 URL에 넣지 않고 브라우저에 보관합니다. 공유 PC에서는 사용 후 **이 기기의 요청 기록 지우기**를 사용합니다. 지우기는 서버 요청 취소나 실습실 종료가 아닙니다. 접수 응답을 놓쳤다면 새 요청을 연속으로 만들지 말고 **상태 다시 확인**, 필요한 경우 **같은 요청으로 접수 확인**을 사용합니다.

## 모임지기 휴대폰 설정

참여자용 `lab.shinick.dev` 앱과 **모임지기용 `k.shinick.dev/lab` 앱**은 서로 다릅니다. 알림을 받을 휴대폰마다 모임지기 앱에서 설정합니다.

1. 휴대폰에서 https://k.shinick.dev/lab 을 열어 홈 화면에 설치합니다. 설치한 앱에서 **실습실 개설 요청함 · 휴대폰 알림 설정**으로 이동합니다.
2. 요청함에서 **본인 이메일(jcpukpyi@gmail.com)의 로그인 코드**로 로그인합니다. 목록 조회에는 보안 키가 필요하지 않습니다. 다른 계정에는 접근을 허용하지 않습니다. 로그인은 최대 24시간이며 Access의 상위 정책에 따라 더 짧아질 수 있습니다.
3. **개설 요청 알림 켜기** → OS의 알림 허용 → 보안 키로 이 기기 등록을 확인합니다.
4. **이 기기에 시험 알림 보내기**를 누르고 앱을 배경으로 보낸 뒤 잠금 화면·알림 센터에서 실제 표시를 확인합니다.
5. 표시를 직접 봤을 때만 **휴대폰에서 실제 알림을 봤어요**를 누릅니다. 이는 본인의 확인 기록이며 OS가 자동으로 배달을 증명하는 기능은 아닙니다.

iPhone·iPad는 iOS·iPadOS 16.4 이상에서 홈 화면에 추가한 웹앱으로 열고 사용자 클릭으로 알림 권한을 요청해야 합니다. [WebKit 공식 안내](https://webkit.org/blog/13878/). Android는 지원되는 Chrome의 앱 설치·홈 화면에 추가를 이용합니다. 브라우저·기기에서 기능을 제공하지 않거나 권한이 거부되면 화면에 안내가 표시됩니다.

설치만으로 알림이 켜지지는 않습니다. 알림 권한 허용, 서버의 기기 등록, 시험 알림 실물 확인까지 마쳐야 합니다. 요청 알림 등록은 요청함 로그인과 별개로 유지되며, 보안 키 삭제·기기 등록 해제·푸시 서비스의 구독 무효화가 있으면 중지됩니다. **요청함 로그아웃**은 본인 로그인 세션을 닫으며, **개설 요청 알림 끄기**는 별도의 알림 등록을 해제합니다. 기존 손들기 알림은 원래 모임 보기 세션 정책을 따릅니다.

## 승인

알림을 누르면 고정된 요청함만 열립니다. 알림 자체에는 승인 토큰이나 참여자 이름·작업 내용이 없습니다.

- **개인 복습**: 모임지기가 **실습실 사양·사용 시간·AI 사용액 상한**을 선택합니다. 사양은 `1 CPU / 2 GiB / 디스크 5 GiB`, `2 CPU / 4 GiB / 디스크 5 GiB`, `4 CPU / 8 GiB / 디스크 10 GiB` 중에서 고르거나 **직접 입력**으로 CPU 코어 수·메모리 GiB·디스크 GiB를 각각 양의 정수로 적습니다. 기본 선택은 1 CPU / 2 GiB / 5 GiB입니다. 요청자가 사양을 결정하지 않으며, 기존 모임 기본 설정도 덮어쓰지 않습니다. AI 상한과 샌드박스 비용은 별개입니다.
- **모임 자리 추가**: 현재 열려 있는 모임을 고릅니다. 새 자리 하나만 추가하며 기존 자리의 파일·터미널·초대 코드를 바꾸지 않습니다. 해당 모임의 사양·모델·사용 한도·종료 시각을 따릅니다. 자리 한도 또는 체험 연결 중인 모임에는 추가하지 않습니다.

**보안 키로 승인하고 열기**는 해당 요청과 선택한 조건에 묶인 일회용 확인을 사용합니다. 이메일로 로그인한 뒤 개설 승인 버튼에서 한 번 확인하며, 별도의 관리자 키 로그인은 요구하지 않습니다. 모임 정책이 바뀌면 이전 확인을 다른 조건의 승인으로 돌려 쓰지 않습니다.

CPU·메모리·디스크도 승인 조건에 포함됩니다. 키 확인 중에는 입력값을 잠그며, 키 확인 뒤 사양을 바꿔 호출하면 거부합니다. 이미 승인한 요청의 사양을 나중에 다른 값으로 덮어쓸 수 없습니다. 사양을 보내지 않는 이전 요청함 화면은 기존 기본값(1/2/5)으로 처리합니다.

직접 입력한 사양은 기존 사양별 스냅샷 준비 흐름을 사용합니다. 해당 사양이 처음이면 준비에 시간이 걸릴 수 있으며, **같은 요청으로 생성 결과 확인**으로 이어갑니다. Daytona 조직 할당량·권한·스냅샷 상태가 맞지 않으면 개설이 거절될 수 있습니다. 작은 사양으로 임의 대체하지 않습니다. [Daytona 공식 사양 안내](https://www.daytona.io/docs/en/scale/).

조직 전체의 남은 용량과 **실습실 1개당 상한**은 별개입니다. Daytona의 기본 컨테이너 상한은 4 vCPU·메모리 8 GiB·디스크 10 GiB입니다. 예를 들어 조직 메모리가 200 GiB 남아 있어도 개별 상한이 8 GiB이면 9 GiB 요청은 거절됩니다. 새 사양의 스냅샷을 만들기 전에 확인 가능한 조직 정책을 조회하고, 상향 승인된 개별 한도가 있으면 그 값을 사용합니다. 정책 조회를 못 하거나 여러 지역 중 대상을 확정할 수 없으면 공급자가 최종 검증하며, 알려진 사양 오류의 숫자만 안전하게 안내합니다. [Daytona 리소스 안내](https://www.daytona.io/docs/en/sandboxes/#resources).

일반 `/lab`에서 개별 한도 때문에 거절되면 **결과 복구**로 접수 상태를 확인한 뒤, **새 수업 입력으로 돌아가기**로 사양을 수정합니다. 예전 버전에서 자원 생성 전 멈춘 기록은 새로고침·보안 키 로그인 뒤 **결과 복구**로 확인할 수 있습니다. 서버가 생성 단계에 들어가지 않았고 실행 중인 작업도 없다고 확인할 때만 이 경로를 열며, 결과가 불명확하거나 이미 자원을 만들기 시작한 요청은 계속 잠급니다. 요청함에서 이미 키로 승인한 조건은 바꾸지 않으므로, 그 경로에서는 수정한 조건을 새 요청으로 승인합니다.

## 요청함 접근 제한과 운영 설정

Cloudflare Access 앱 `실습실 요청함 · 모임지기 전용`은 `k.shinick.dev/lab/requests`와 `k.shinick.dev/api/lab/open/manager`만 보호합니다. 허용 정책은 본인 이메일 하나인 `owner-only`이며, 이메일 PIN으로 로그인합니다. 참여자용 `/lab/request`, 자기 요청 조회, 샌드박스 게이트웨이 `/p/`와 다른 관리 페이지는 이 앱에 포함하지 않습니다.

Worker는 Access가 전달한 JWT의 서명·발급자·앱 AUD·만료·본인 이메일을 확인합니다. 이메일 헤더만으로는 허용하지 않으며, 설정이 없거나 검증에 실패하면 닫힌 상태로 거부합니다. `LAB_OPEN_ACCESS_TEAM`, `LAB_OPEN_AUDIENCE`, `LAB_OPEN_OWNER_EMAIL`은 `wrangler.jsonc`에 있습니다. 앱을 재생성하면 AUD도 갱신해야 합니다. 기존 `/api/lab/open/list` 등 보호 경로 밖의 관리 호출은 거부합니다.

이메일 로그인에는 일반 관리 토큰을 발급하지 않습니다. 승인된 요청을 이어갈 때만 서버 내부에서 고정 작업 ID와 서명 때 저장한 조건으로 생성 절차를 호출합니다. 서명하지 않은 대기 요청은 이어갈 수 없습니다. 일반 `/lab` 관리 권한은 기존 보안 키 로그인 정책을 따릅니다.

원복 시 Worker 코드·설정과 이 Access 앱을 함께 확인하세요. 예전 버전은 요청함에서 보안 키 로그인을 추가로 요구합니다. Access 앱을 지우더라도 새 Worker의 JWT 검증이 실패하므로 요청함이 공개되지는 않습니다.

응답이 늦으면 **같은 요청으로 생성 결과 확인**을 사용합니다. 생성 부작용 전 요청·고정 작업 ID를 저장하고, 이미 실행했는지 모르는 작업은 자동으로 새 ID로 다시 실행하지 않습니다. 결과가 계속 확인되지 않으면 `/lab`의 모임 목록에서 준비·정리 상태를 확인합니다. 실패한 자리의 수리·교체는 기존 관리 절차를 이용합니다.

대기 요청은 최대 128건이며, 같은 출처의 새 요청은 10분에 5건까지입니다. 목록은 승인 대기를 우선해 최대 128건을 보여주고, 표시 한도에 도달하면 보관 건수도 알립니다. 요청 기록은 48시간 뒤 정리됩니다. 새 자리를 추가해도 기존 수업 터미널의 선택 대상은 자동으로 바꾸지 않으므로 모임지기가 새 자리를 확인해 포함합니다.

## 알림이 빠지거나 늦을 때

웹 푸시로 모든 상황의 도착을 보장할 수는 없습니다. 전원 꺼짐, 통신 단절, 집중 모드·절전·브라우저 권한, 푸시 서비스 장애, 구독 만료가 표시를 막을 수 있습니다.

- 요청함을 기준 기록으로 사용합니다. 푸시 실패나 앱 종료가 요청을 지우지 않습니다.
- 알림 전송은 영속 기록과 재시도를 사용하고, 기기를 나중에 등록해도 미처리 요청을 다시 확인합니다. 서버 재시작 때 메모리만으로 작업을 복원하지 않습니다.
- **푸시 서비스 접수**와 **휴대폰 실제 표시**를 구분합니다. 시험 알림은 직접 확인해야 합니다.
- 구독이 무효화되면 다시 등록합니다. 휴대폰·브라우저 데이터 삭제·알림 권한 변경 후에는 시험을 다시 합니다.
- 미처리 요청은 고정된 일반 알림으로 재안내합니다. 알림을 보았다는 사실과 승인·실습 성공을 혼동하지 않습니다.
- 끄기·키 삭제 전에 이미 푸시 서비스에 접수된 알림이 뒤늦게 표시될 수 있습니다. 그 알림은 실습실 개설 권한을 주지 않습니다.

## 운영 검증 범위

자동 검사와 가상 화면은 요청 보관·조건에 묶인 서명·중복 생성 방지·기존 자리 보존·알림 재시도·고정 알림 이동 경로를 각각 확인합니다. 실제 휴대폰의 설치·NFC·OS 표시·네트워크·과금 공급자 응답은 모임지기 기기에서 별도로 점검해야 합니다. 테스트 알림을 보지 않고 수신 확인을 대신 표시하지 않습니다.
