# AI 실습 모임을 학습 플랫폼으로 발전시키기 위한 UX·OSS 조사

조사일 2026-10-16 · 기준 코드 `gw-shinick`의 `2e45f2e` · 대상: 초보 참여자 2~5명, 모임지기 1명, 40~50분 온라인 모임.

## 판단

지금 투자 효과가 클 것으로 보는 순서는 **모임지기 전용 시연실 → 참여자 한 화면 구성 → 현재 단계와 도움 대기열 → 제출·복습**이다. 현재 시스템에는 실습실, 자동 미리보기, 동의 기반 제어, 명령 전달, 파일 보관, 조교 권한이 있다. 이 기능들을 수업의 한 흐름으로 연결하는 작업이 우선이다.

포크는 비교·추적용으로 보관한다. 실제 도입은 기능마다 기존 구현 확장, 독립 구현, 라이브러리, 별도 서비스 중에서 고른다. 작은 상태 표시나 투표까지 대형 LMS를 설치할 필요는 없다. 이 문서의 편의성·우선순위 평가는 우리 수업에 대한 **설계 가설**이며 사용자 실험 결과가 아니다.

## 관찰 범위

- **실제 화면 관찰:** Aside로 Moodle 공식 Mount Orange 데모의 안내 → 공개 참여자 계정 → 강좌 목차 → 할 일 조건 펼치기를 확인했다. 공개 데모 계정으로 읽었으며 완료 체크·과제 제출·메시지 전송·강좌 수정은 하지 않았다. 데모는 매시간 초기화된다. [관찰한 강좌](https://school.moodledemo.net/course/view.php?id=72)
- **소스 확인:** 아래 고정 커밋의 관련 파일을 읽었다. 존재하는 기능을 확인한 것이며 해당 시스템 전체의 보안·품질 검증은 아니다.
- **문서 확인:** 각 프로젝트의 공식 문서와 원본 README·라이선스를 사용했다. Canvas·Open edX·BigBlueButton을 직접 설치해 수업을 진행한 것은 아니다.
- **추론:** 사용자가 겪은 화면 전환 부담, 따라가기 실패, 운영 도구 혼동과 연결해 우선순위를 정했다. 실제로 시간을 얼마나 줄이는지는 다음 파일럿에서 측정해야 한다.

Moodle 데모의 실제 화면에는 왼쪽 목차, 가운데 활동, 오른쪽 보조 정보가 함께 있었다. 목차와 완료 조건은 유용한 참고지만, 이 세 영역을 편집기와 함께 그대로 늘어놓으면 노트북의 실습 공간이 줄어든다. 우리 화면은 현재 단계와 주 작업을 먼저 보이고 보조 정보는 접어서 여는 구성이 적합하다는 판단이다. 공개 데모에서 본 한 장면에 대한 관찰이며 Moodle 전체의 사용성 평가로 일반화하지 않는다.

## 기능별로 붙일 수 있는 OSS

현재 앱은 Workers/State Durable Object, Daytona, Cloudflare Realtime, 브라우저 JS 중심이다. `package.json`에는 React 런타임이 없다. React 위젯은 작은 별도 번들·분리 화면 등의 연결 작업이 필요하다. 아래 난이도는 이 구조에 대한 상대적 추정이며 설치·통합 실험을 마친 견적이 아니다.
